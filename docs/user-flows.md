# STOG 사용자 흐름 초안

> 상태: draft  
> 이 문서는 `product.yaml`의 사용자 흐름을 화면, Android 입력, API, DB
> 관점으로 풀어쓴 작업 문서다. 확정 기준은 `glossary.yaml`,
> `product.yaml`, `architecture.yaml` 순서로 판단한다.
>
> 공유 담기와 여행 가이드 AI의 세부 범위는 아직 변경될 수 있다. 이
> 문서의 제안은 구현 전 검토 대상이며, YAML의 `open_items`를 대신하지
> 않는다.

## 1. 공통 원칙

1. 공유 수신 순간에는 네트워크 검색을 기다리지 않는다.
2. Android가 받은 원본 텍스트, URL, 파일을 먼저 STOG 소유 저장소에
   보존한다.
3. 장소명·주소·좌표가 일부만 있어도 `link_block`으로 저장한다.
4. 검색 결과나 AI가 만든 장소명은 후보이며, 사용자 확인 전에는
   `place`와 `itinerary_item`으로 확정하지 않는다.
5. 미완성 항목도 사용자에게 즉시 보인다. "등록되지 않음"이 아니라
   "원본 저장 완료, 장소 확인 필요"로 표시한다.
6. AI는 사실을 임의로 만들지 않는다. 좌표, provider ID, 영업 여부와
   같은 사실은 검색 결과 또는 허용된 내부 데이터에서 확인한다.
7. AI의 제안은 사용자 확인 뒤에만 일정과 DB를 변경한다.
8. provider 결과의 장기 저장·재사용·공개는 해당 provider와 데이터셋의
   조건을 확인한 뒤 허용한다.

## 1.1 기능 이름과 가시성 원칙

기능은 내부 구현명이 아니라 사용자가 다음 행동을 바로 이해할 수 있는
이름으로 노출한다. 문서와 UI의 한국어 명칭은 glossary의 `ko`를
사용하고, 코드 식별자는 `en`을 사용한다.

| 사용자에게 보이는 이름 | 내부 개념 | 사용자가 이해해야 하는 행동 |
|---|---|---|
| 공유 담기 | `share_import` | 다른 앱의 원본을 STOG에 저장 |
| 일정 바구니 | `basket` | 아직 일정에 배치하지 않은 후보 모음 |
| 일정에 배치 | `itinerary_item` 생성 | 후보를 날짜와 순서가 있는 일정으로 이동 |
| 카드 대시보드 | `itinerary` 편집 | 순서 변경과 중간 삽입 |
| 여행 모드 | `trip_mode` | 이동 기록 수집 상태 확인 |
| 촬영 화면 | `capture_screen` | 현재 `spot`과 사진 기록 |
| 나의 여행 | `archive` | 종료된 여행과 사진 확인 |
| 여행 가이드 AI | `travel_guide_ai` | 현재 상황을 설명하고 다음 행동 제안 받기 |

내부 상태명(`resolved`, `manual`, `unresolved`)을 그대로 사용자에게
노출하지 않는다. 사용자가 지금 무엇이 되었고 다음에 무엇을 해야 하는지
보이도록 상태를 번역한다.

| 내부 상태 | 화면에 보이는 상태 | 사용자의 다음 행동 |
|---|---|---|
| 원본 저장 완료 | 저장됨 · 장소 확인 중 | 계속 다른 앱을 사용 |
| 후보 검색 중 | 장소 후보를 찾는 중 | 기다리지 않고 나중에 확인 |
| `resolved` | 장소 확인 필요 또는 일정에 배치 가능 | 후보 확인 |
| `manual` | 직접 입력한 장소 | 주소와 좌표 확인 |
| `unresolved` | 장소를 찾지 못함 | 직접 검색 또는 나중에 확인 |
| 후처리 실패 | 다시 확인 필요 | 재시도 또는 직접 입력 |
| AI 처리 중 | 일정 검토 중 | 현재 계획을 계속 사용 |
| AI 실패 | 일정은 유지됨 | 수동 편집 또는 다시 요청 |

가시성 규칙:

1. 공유 직후 빈 화면이나 무한 로딩만 보여주지 않는다. 저장 완료
   상태와 원본 항목을 즉시 보여준다.
2. 장소 확인이 필요한 항목 수를 `basket` 진입점에 표시한다.
3. 앱 진입 시 확인 패널을 한 번 표시하되, 닫아도 `basket`에서 다시
   찾을 수 있게 한다.
4. `unresolved` 항목은 숨기거나 조용히 삭제하지 않는다.
5. AI 가이드는 여행 전에는 카드 대시보드의 일정 검토 지점에서,
   여행 중에는 현재 상황과 연결된 명확한 진입점에서 보인다.
6. AI가 자동으로 일정이나 장소를 바꾸지 않았다는 사실을 화면에서
   확인할 수 있어야 한다.
7. P0 기능은 기본 화면의 주요 진입점에 두고, P1 기능은 P0 흐름 안에서
   발견할 수 있게 한다. P2 기능을 첫 화면의 핵심 동작보다 앞에 두지 않는다.

### AI 입력·출력 개인정보 계약

여행 가이드 AI에는 사용자의 요청을 처리하는 데 필요한 최소 자료만
전달한다.

| 자료 | 기본값 | 조건 |
|---|---|---|
| 확인된 장소와 남은 일정 | 포함 | 일정 검토·대체 장소 제안에 필요 |
| 현재 위치 | 제외 | 여행 중 사용자가 요청하고 동의한 경우에만 제한적으로 포함 |
| 현재 시각 | 제외 | 운영 상태와 일정 검토에 필요한 경우 포함 |
| 이동 스타일·성향 축 | 포함 | 추천 정렬에 필요한 최소 값만 포함 |
| 공유 원본 파일 | 제외 | 사용자가 특정 원본 분석을 요청한 경우에도 필요한 부분만 추출 |
| 정확한 주소·좌표 | 최소화 | 후보 검색에 필요한 정밀도로 제한 |
| 전체 행동 이력·전체 대화 | 제외 | 질문 처리에 필요한 관련 항목만 포함 |
| 인증 토큰·provider secret | 항상 제외 | 어떤 AI 요청에도 포함하지 않음 |

AI는 장소 사실을 새로 확정하지 않는다. 검색·공공데이터·사용자 확인
결과를 사실로 사용하고, 불확실한 값은 `확인 필요`로 표시한다. AI
응답은 제안과 action preview를 반환하지만, 실제 `itinerary` 변경은
사용자가 버튼을 누른 뒤 일반 API가 수행한다.

AI 요청과 결과의 보관 기간·모델 로그·삭제 범위는 개인정보 보존 정책과
AI provider 조건을 확인하기 전에는 장기 보관하지 않는다.

## 2. 공유 담기 데이터 양식 초안

공유 담기(`share_import`)는 입력 형식이 출처마다 다르므로, provider
객체를 그대로 장소로 변환하지 않고 공통 양식에 맞춰 정규화한다.

| 항목 | 수신 즉시 채움 | 후처리로 채움 | 비고 |
|---|---|---|---|
| 출처 | Android action, MIME, 호출 앱 추정값 | 사용자 확인 또는 adapter 보정 | 진위의 근거로 단독 사용하지 않음 |
| 원본 URL | 텍스트와 `getData()`에서 추출 | 단축 URL 해석 | 원본 URL은 항상 보존 |
| 원본 텍스트 | `EXTRA_TEXT` | 장소명 후보 추출 | 줄 순서와 빈 줄 수에 의존하지 않음 |
| 원본 HTML | `EXTRA_HTML_TEXT` | 링크·제목 보정 | 없을 수 있음 |
| 첨부 파일 | `EXTRA_STREAM`, `ClipData` | 내부 미리보기 생성 | `content://` URI는 즉시 복사 |
| 제목 | 공유 텍스트 또는 OG 정보 | 사용자 수정 | 자동 확정하지 않음 |
| 주소 | 공유 텍스트에 있을 때 | provider 검색 또는 직접 입력 | 없을 수 있음 |
| 좌표 | 공유 payload에 있을 때 | Kakao/Naver 검색 또는 사용자 선택 | 확인 전 동선 계산에 사용하지 않음 |
| `cell_id` | 좌표가 있을 때 계산 | 좌표 확정 뒤 재계산 | API는 16진 문자열 |
| 분류 | 공유 정보에 있을 때 | provider 또는 사용자 확인 | 모르면 비워 둠 |
| 미리보기 | 공유 파일 또는 허용된 OG 정보 | 사용자 확인 | source별 저장·표시 조건 확인 필요 |
| 처리 상태 | 원본 저장 완료 | `resolved`, `manual`, `unresolved` | 화면 상태와 DB enum 매핑은 별도 결정 |
| 사용자 결정 | 없음 | 확인, 삭제, 직접 입력, 보류 | 확인 시각과 선택 결과 보존 |

### 2.1 단계별 상태

```text
공유 수신
  -> 원본 저장
  -> link_block 표시
  -> 장소 후보 추출
  -> provider 검색 또는 직접 입력
  -> 사용자 확인
  -> resolved / manual / unresolved
  -> basket 유지
  -> itinerary_item 배치
```

현재 `basket_items`는 최종 바구니 항목을 담는 구조다. 원본 payload,
여러 장소 후보, 사용자 결정 이력, 처리 재시도 상태까지 저장할 컬럼은
아직 충분히 정의되지 않았다. 따라서 다음 DB 작업에서 아래 두 방향 중
하나를 결정해야 한다.

- `basket_items`에 원본·후보·결정 정보를 JSON과 상태 컬럼으로 확장
- 원본 공유 항목과 후보·결정 이력을 별도 저장하고 확정 결과만
  `basket_items`와 `places`에 연결

이 결정 전에는 새 테이블이나 컬럼을 코드에서 임의로 만들지 않는다.

## 3. Android 공유 수신 흐름

### 3.1 입력 수신

Android 수신부는 다음 값을 모두 확인한다.

- `ACTION_SEND`
- `ACTION_SEND_MULTIPLE`
- `EXTRA_TEXT`
- `EXTRA_HTML_TEXT`
- `EXTRA_STREAM`
- `Intent.getData()`
- `ClipData`
- MIME type

MIME type이나 호출 앱 이름만으로 payload 내용을 확정하지 않는다.
공유된 `content://` URI는 장기 사용을 위해 즉시 앱 내부 저장소로
복사한다. 파일 개수와 크기 제한도 실제 bytes를 읽기 전에 확인한다.

### 3.2 즉시 표시

공유 수신부는 다음까지만 빠르게 수행한다.

1. 공유 입력을 읽는다.
2. 원본을 앱 내부 저장소에 복사한다.
3. 최소 제목과 URL을 추출한다.
4. `link_block`을 `basket`에 저장한다.
5. 사용자에게 "저장됨 · 장소 확인 중" 상태를 보여준다.
6. 외부 앱으로 돌아간다.

provider 검색, AI 호출, 여러 장소 분석은 이 수신 흐름에서 기다리지
않는다. 네트워크가 실패해도 원본과 `link_block`은 남아야 한다.

### 3.3 후처리 완료 알림

후처리 결과가 준비되면 다음 진입 시점에 알려준다.

- 앱 아이콘의 대기 항목 표시
- 앱 진입 시 확인 패널
- 확인이 필요한 항목을 source별로 묶어 표시

확인 패널을 닫아도 원본과 대기 항목은 삭제하지 않는다. 사용자는
`basket`에서 나중에 다시 확인할 수 있어야 한다.

## 4. 출처별 처리

### 4.1 Kakao 지도 공유 원본

예상 입력:

```text
[카카오맵] 장소명
주소
https://kko.to/...
```

처리 순서:

1. 원본 텍스트와 URL 저장
2. URL과 텍스트에서 장소명·주소 후보 추출
3. 서버에서 Google Places API (New) Text Search
4. 장소명·주소·좌표·분류를 후보로 표시
5. 사용자 확인 후 `place` 또는 `manual` 항목으로 확정

줄 번호, 빈 줄 수, 특정 문구의 위치는 계약으로 취급하지 않는다.
Kakao 지도는 공유 원본 carrier로만 사용하며 장소 provider로 호출하지 않는다.
Google Places 결과의 장기 보관과 표시 범위는 provider 약관 확인 전까지
canonical 데이터 보존 정책으로 확정하지 않는다.

### 4.2 Naver 지도 공유

예상 입력:

```text
[네이버지도] 장소명
주소
https://naver.me/...
```

Naver 지도 공유는 외부 앱에서 들어오는 원본 입력 source로만 지원한다.
원본을 먼저 저장하고, 텍스트·URL·첨부 정보를 종합한 뒤 장소 후보
검색은 Google Places API (New)를 사용한다. Naver API를 별도 검색 provider로
호출하지 않으며, 후보는 자동 확정하지 않는다.

### 4.3 Instagram

Instagram 공유에서 항상 받을 수 있다고 가정할 수 있는 값은 URL 또는
일부 텍스트뿐이다. 다음 정보는 수신 계약으로 가정하지 않는다.

- 게시물 전체 caption
- 작성자
- 게시물 장소
- carousel 내부 장소 목록
- 원본 미디어의 장소 metadata

처리 순서:

1. Instagram URL과 수신 텍스트를 원본으로 저장
2. 링크 항목을 `basket`의 Instagram section에 즉시 표시
3. 텍스트에서 장소명 후보를 찾을 수 있으면 후보로 저장
4. 여러 장소가 있으면 여러 후보로 표시
5. 이미지에만 정보가 있으면 자동 확정하지 않고 사용자 입력을 요청
6. 앱 진입 시 확인 패널에서 장소별로 `[이 장소가 맞아요]`,
   `[삭제]`, `[직접 입력]`을 제공
7. 확인된 장소만 `itinerary_item`으로 옮길 수 있게 한다

OCR이나 게시물 전체 분석을 공유 수신의 필수 단계로 두지 않는다.

## 5. `basket` 표시와 재활용

### 5.1 화면 분리

현재 작업안은 하나의 여행 `basket` 안에서 출처별 목록을 화면 section으로
분리하는 것이다. DB 테이블이나 여행 자체를 출처별로 나누지 않는다.
사용자는 같은 `basket` 안에서 각 목록을 따로 확인하고, 확인된 항목만
일정에 배치한다.

- 네이버 지도
- 카카오 지도
- Instagram
- 앱 내부 검색
- 직접 입력

각 section에는 출처와 처리 상태를 표시하고, `확인 필요` 항목을 먼저
보여준다. 일정에 배치할 때는 하나의 `basket`에서 통합한다. 출처별
독립 목록이 서로 다른 여행 계획을 뜻하지 않으므로 별도 여행이나 별도
바구니를 만들지 않는다.

이 결정은 **화면 분리 결정**이며, 원본·후보·결정 이력을 어떤 DB 구조로
보존할지는 별도의 schema 결정이다.

### 5.2 장소 확정과 내부 재사용

완성된 데이터는 다음 세 종류를 구분해 저장한다.

1. 사용자가 직접 입력하거나 수정한 정보
2. 사용자가 확인한 장소와 확인 시각
3. provider에서 받은 원본과 검색 후보

사용자 확인은 장소 선택의 기준이지 provider 콘텐츠의 저장·재사용·
재배포 허가를 대신하지 않는다.

따라서 provider 약관을 확인하기 전에는 다음처럼 보수적으로 처리한다.

- 사용자 입력 제목·메모·확인 action은 내부 자료로 재활용할 수 있다.
- provider 원본·검색 후보·provider ID·주소·좌표는 요청 범위 또는
  제한된 처리 보관으로만 사용한다.
- 다른 사용자에게 보여주는 자료는 사용자 생성 정보와 라이선스를
  확인한 공공데이터만 사용한다.
- provider가 명시적으로 허용한 경우에만 해당 필드를 재사용 가능한
  내부 장소 자료로 승격한다.

provider별 승격 조건과 보관 기간은 약관 확인 뒤 별도로 기록한다.

### 5.3 현재 보관 정책 결정

약관 확인 전의 기본 정책은 **provider 자료를 재활용 가능한 공용
장소 자료로 승격하지 않는 것**이다.

| 자료 | 기본 보관 범위 | 다른 사용자에게 재사용 |
|---|---|---|
| 사용자 입력·수정·확인 결과 | 사용자 여행 범위와 필요한 내부 기록 | 사용자 공개 범위와 개인정보 정책에 따름 |
| 공유 원본 URL·텍스트·파일 | 원본 확인과 후처리에 필요한 제한된 범위 | 금지 |
| provider 검색 후보·ID·주소·좌표 | 처리 중 또는 약관상 허용된 범위 | 금지 |
| 라이선스 확인 공공데이터 | provenance와 license를 함께 보관 | 조건과 출처 표기 준수 |
| provider가 재사용을 허용한 필드 | 허용된 필드·기간·표시 조건 안에서만 | 계약·약관 조건 안에서만 |

이 정책은 법적 허가를 새로 부여하는 결정이 아니라, 확인되지 않은
권리를 가정하지 않기 위한 구현 기본값이다.

## 6. UF-01 여행 전 계획

### 시작 조건

- 사용자가 외부 앱에서 STOG를 공유 대상으로 선택한다.
- 또는 앱 안에서 장소를 검색한다.

### 흐름

1. Android가 공유 원본을 받는다.
2. 원본과 최소 제목·URL을 즉시 저장한다.
3. `basket`에 source별 `link_block`을 표시한다.
4. 후처리 결과가 준비되면 앱 진입 확인 패널에 알린다.
5. 사용자가 장소 후보를 확인하거나 직접 입력한다.
6. 확인된 항목만 일정 항목으로 배치한다.
7. 카드 대시보드에서 순서를 바꾸고 중간에 추가한다.
8. 좌표가 없는 `unresolved` 항목은 동선 계산에서 제외하고 표시한다.
9. AI가 이동시간·체류시간·영업 상태를 바탕으로 검토한다.
10. AI는 현재 계획을 바꾸지 않고 조정안을 제시한다.
11. 사용자가 조정안을 선택한 뒤 일정과 `trail`에 반영한다.

### 실패 흐름

- 공유 수신 실패: 원본이 없으므로 저장 실패를 알린다.
- 장소 후보 0개: `unresolved`로 보관하고 직접 입력을 제공한다.
- 후보 1개: 자동 확정하지 않고 확인을 요구한다.
- 후보 여러 개: 기본 선택 없이 사용자가 0개 이상 선택한다.
- 검색 timeout: 원본과 `link_block`은 유지하고 재시도한다.
- AI timeout: 현재 일정은 유지하고 수동 편집을 제공한다.

## 7. UF-02 여행 중 기록과 여행 가이드 AI

여행 가이드 AI는 사용자가 모은 장소와 현재 상황을 바탕으로 다음
행동을 선택하도록 돕는 기능이다. 자유 대화만 제공하는 기능이 아니라
지도·일정 변경과 연결되는 제안 기능으로 정의한다.

### 호출 시점

#### 여행 전

- 카드 대시보드의 일정 검토 버튼
- unresolved 항목을 확인한 뒤 일정 배치 요청
- 이동시간 초과 또는 영업시간 충돌 검토

#### 여행 중

- 사용자가 하단 AI 입력창을 열고 질문
- 현재 장소가 휴무·마감으로 확인됨
- 일정이 늦어져 다음 장소 조정이 필요함
- 남은 일정 주변의 식사·휴식 장소를 찾음

여행 중 자동으로 대화창을 계속 열지 않는다. 사용자 요청 또는 명확한
상황 알림 뒤에 제안 카드로 진입한다.

### 입력

기본 입력:

- 사용자가 확인한 `place`와 `itinerary_item`
- 남은 일정과 고정한 일정 항목
- 사용자가 요청한 경우의 현재 좌표와 시각
- `mobility_style`
- 영업 상태·접근성·날씨처럼 최신 확인이 필요한 정보
- 사용자의 성향 축과 명시한 조건

기본적으로 보내지 않는 정보:

- 원본 공유 파일 전체
- 인증 정보
- 필요 이상의 정확한 좌표
- 전체 대화와 전체 행동 이력
- 확인되지 않은 장소를 확정 사실처럼 표현한 값

### 출력

AI 응답은 다음을 함께 제공한다.

- 추천 또는 조정 내용
- 근거가 된 확인 정보
- 최신 확인 시각
- 불확실하거나 추가 확인이 필요한 항목
- 예상되는 이동·체류 영향
- 사용자가 선택할 수 있는 행동

가능한 행동:

- 장소를 일정에 추가
- 기존 장소와 교체
- 순서 조정안 미리보기
- 다음 방문지로 선택
- 지도에서 후보 보기
- 무시 또는 나중에 보기

AI가 직접 `itinerary_items`를 수정하지 않는다. 사용자가 행동을
확정하면 일반 API가 DB를 변경하고 변경 이력을 남긴다.

### 여행 중 예시

```text
사용자: "지금 장소가 문을 닫았어. 주변에서 쉬었다 갈 곳 있어?"

앱:
  현재 위치와 남은 일정 확인
  -> 주변 후보와 운영 상태 조회
  -> 사용자 성향과 mobility_style 반영
  -> 추천 카드 2~3개 표시
  -> [다음 장소로 교체] [일정에 추가] [무시]
```

AI는 없는 영업시간·가격·쿠폰을 만들어내지 않는다. 최신 확인이
불가능하면 "확인 필요"로 표시한다.

## 8. UF-03 여행 후 기록과 공유

1. 여행 종료 시 `trip_mode`가 `ended`가 된다.
2. 종료된 여행은 `archive`에 표시한다.
3. `trail`과 사진을 지도와 게시물 형태로 보여준다.
4. 사용자가 `visibility`를 선택한다.
5. 공개된 여행은 다른 사용자가 좋아요를 남기거나 일정으로 복사할
   수 있다.
6. 외부 앱으로 사진을 보낼 때는 `share_export`로 파일만 전달한다.

공유 담기로 들어온 provider 데이터와 사용자가 직접 만든 사진·좌표는
같은 저장 정책으로 취급하지 않는다.

## 9. 지연·오프라인·실패 처리

| 상황 | 사용자에게 즉시 보이는 것 | 나중 처리 |
|---|---|---|
| 공유 직후 | 원본 저장 완료와 `link_block` | 장소 후보 검색 |
| 네트워크 없음 | 대기 상태와 원본 | 연결 후 재시도 |
| 장소 후보 없음 | 미확인 항목 | 직접 입력 |
| 후보 여러 개 | 확인 필요 패널 | 사용자가 선택 |
| provider 오류 | 원본 유지와 재시도 | provider별 재처리 |
| AI 오류 | 현재 일정 유지 | 수동 편집 또는 재요청 |
| 사용자가 패널 닫음 | 대기 항목 수 | `basket`에서 재진입 |

공유 수신 화면은 외부 앱에서 실행되므로 긴 작업, 반복 재시도,
provider 검색, LLM 호출을 동기적으로 실행하지 않는다.

## 10. 구현 전 결정사항

다음은 이 문서의 초안만으로 확정하지 않는다.

1. **현재 작업안:** 여행 가이드 AI는 기존 F-09의 일정 검증·동선 생성과
   같은 P1 흐름의 확장으로 다룬다. 별도 기능 ID를 만들지 않는다.
   사용자가 확정하기 전까지는 canonical 결정이 아니다.
2. 원본 payload·후보·사용자 결정 이력을 `basket_items`에 둘지,
   별도 저장 구조로 둘지
3. source별 `basket` 분리가 화면 section인지, 실제 독립 목록인지
4. provider 검색 결과 중 어떤 필드를 재사용 가능한 내부 자료로
   보관할지
5. AI 호출 시 현재 좌표·시각·성향·그룹 정보를 어디까지 보낼지
6. AI 제안의 최신성 표시와 사용자 확인 UI를 어느 수준까지 P1에
   포함할지

이 문서에서 미결정 항목을 임의로 닫지 않는다. 결정되면 해당 YAML의
`decisions`와 `CHANGELOG.yaml`에 반영한다.
